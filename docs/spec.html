1. Intent

Example utterance:

“Please research the definition of an agentic harness. Do a complete writeup and generate an HTML guide with the results.”

Expected outcome: an HTML guide committed to a private repo, without touching a phone, laptop, or terminal.

Non-goals for v1

  • Plaud’s AI summarization. The NotePin S is a wearable microphone here, not a note-taking product.
  • Sub-minute latency. Minutes are fine.
  • Multi-user support, voice output, conversational back-and-forth.

Success criteria

#Criterion
S1Recording stops → audio lands in the vault repo with zero human action
S2Short (<30s) command recordings survive the pipeline intact
S3Transcript is accurate enough to route without correction
S4Agent output is committed back to the vault repo
S5Failures are visible; no recording is silently dropped
S6The same recording is never processed twice

2. Architecture

The controlling insight. The NotePin S has its own 2.4 GHz Wi-Fi radio and can upload directly to Plaud Cloud with no phone involved. Combined with a Plaud Web fetcher (ADR-002), the iPhone drops out of the design entirely.

Git is the boundary. The two halves never talk directly — only through commits.

  • The Plaud credential lives on WarDog, not Forge. The seeded browser session never touches the AI server.
  • Forge can be offline without losing recordings. This is the main thing the split buys.
  • Both hosts push to the same repo. Disjoint paths (inbox/ + .state/ vs processed/), but every push is pull --rebase then retry.
  • Two deploy keys, one per host, independently revocable.

Assumption A3: WarDog is always-on with outbound internet. If it sleeps, latency becomes “whenever WarDog is awake.” Confirm via T-24.

2.2 Why local transcription, not Plaud’s

AutoFlow requires more than 200 words of spoken content to trigger. A 10-second command is ~25 words. Short command recordings will arrive with no Plaud transcript at all.

This is load-bearing: we cannot depend on Plaud’s transcript. Forge runs faster-whisper locally. That is also the desired outcome — it removes the dependency on Plaud’s AI tier and keeps command text off their servers.

Assumption A1: Forge can run small.en on sub-2-minute clips in reasonable time. If Forge is thin, downgrade to base.en. Confirm via T-21.

On the iOS sub-repo question: keep ios/ as a plain directory, not a submodule. A submodule buys independent versioning we don’t need and costs a detached-HEAD footgun on every clone. If the app ever ships independently, split it then — cheap later, expensive now.

Assumption A2: plain git, no LFS. A 1-minute MP3 at 64 kbps is ~500 KB; at 10/day that’s ~1.8 GB/year. Revisit if long-form recordings become common.

Pipeline status

raw → transcribed → routed → executed → published, or → failed at any point. Status lives in each recording’s metadata JSON, so every stage is resumable and idempotent after a crash.

4. Components

ingest/ — Plaud → vault WarDog

Runs on a systemd timer, every 2 minutes. This is the whole of WarDog’s job — it never transcribes, never routes, never runs an agent. It gets audio into git and stops.

flow
plaud_web.py list --days 2 --json   # candidates
  → filter vs .state/seen.jsonl     # dedupe
  → plaud_web.py audio <id>         # time-limited URL
  → download, sha256, metadata      # status: raw
  → append ledger, commit, push
  • Poll, don’t push. No webhook is documented for personal Plaud accounts — they appear only in the enterprise workflow product. Device sync latency dominates anyway.
  • Ledger before commit, commit before processing. The recording is durable in git before any work is attempted on it.
  • Download URLs are time-limited. Fetch immediately; never persist the URL.
  • Python 3.11+ throughout. The fetcher is a module in this repo, not an external binary. No Node dependency at all now that the CLI is gone.

Risk R1. The fetcher depends on Plaud’s web app, which can change without notice. Mitigations: authenticate via Playwright but call the JSON API rather than scraping the DOM (a narrower, more stable target); keep the T-06 discovery report so a break can be diagnosed by re-running recon; and treat T-72’s session health check as load-bearing. The failure is loud at the fetcher and silent everywhere else — nothing downstream can tell “no new recordings” from “login broken.”

plaud_web.py — the fetcher auth + list implemented

Recon ran 2026-07-28 against the unbound free account — the web app seeds three demo files, which was enough to observe auth, the list endpoint and the record schema. Auth, listing and whoami are implemented and unit-tested against captured payloads. The audio download path is the one thing still unknown (T-06b).

Committed — the contract ingest depends on

Stable regardless of what recon finds, because it is our design, not Plaud’s. list --json emits a normalized shape whatever the upstream field names turn out to be, so no other component learns Plaud’s vocabulary.

list --json
{
  "recordings": [
    { "id": "…", "name": "…",
      "created_at": "2026-07-28T14:22:11Z",

Exit codes — what makes silent failure tractable

CodeMeaningIngest’s response
0Successproceed
2Usage errorbug; alarm
3Session expired / auth failedalarm loudly — needs re-seeding
4Network or transient upstream errorretry next tick, quiet
5Unexpected — upstream likely changedalarm; re-run T-06 recon

Code 3 exists because it is the difference between “no new recordings” and “login broken,” and those are indistinguishable from outside. Without it, R1’s failure mode is a pipeline that goes quiet and nobody notices for a week.

Observed — the endpoint layer recon done

#QuestionAnswer from recon
E1Cookie or bearer?Bearer. Authorization: Bearer <workspace_token>
E2requests or browser?Playwright ctx.request — requests isn’t in the fetchers venv, and the browser context shares cookies anyway
E3Pagination?skip / limit, with data_file_total for the bound
E4Download shape?❓ Unobserved — see T-06b
E5Server-side prep needed?⚠️ Probably yes. Every record carries ori_ready, and it was false on all three demo files
E6Short recordings listed normally?❓ Needs a real recording — this is Q5

Auth flow. The web app does a three-step dance: POST /auth/access-token → GET /team-app/workspaces/list → POST /user-app/auth/workspace/token/<ws_id>. Rather than reimplement it, the fetcher harvests the Authorization header off a live request after loading the app.

Useful consequence: the workspace token lives 24h but its refresh token lives 30 days, and the browser performs the refresh. Practical session lifetime is ~30 days, not 24 hours, and the fetcher never touches token renewal. That is most of Q2 answered ahead of schedule.

endpoints in use
GET  /user/me          → data_user{email,…}, data_state{is_bind,…}
GET  /file/simple/web  ?skip&limit&is_trash=0&sort_by=start_time&is_desc=true
                       → {status, data_file_total, data_file_list[]}

Record schema

Plaud’s names stop at _normalize — nothing downstream sees them.

PlaudOursNote
ididhex string
filenamenamemay be empty
start_timecreated_atms epoch → ISO-8601 UTC, second precision
durationduration_secondsms, not seconds
ori_readyori_readyoriginal audio prepared? — E5 depends on it
filetypefiletypee.g. audio/mp3
file_md5md5integrity check on download

Two millisecond traps: duration and start_time are both ms, and naively treating either as seconds produces plausible-looking garbage. Also, application errors arrive as HTTP 200 with a non-zero status field — the transport layer checks the body, not just the status line.

T-06b — the remaining unknown

The download path was never triggered: the account has no exportable recording. ori_ready: false on every demo file is E5 made concrete — the original audio is not necessarily sitting there ready to fetch.

On arrival day, re-run recon against a real recording and export its original audio, watching for the call that flips ori_ready, any polling, and whether the final URL is a presigned CDN link or a stream from api.plaud.ai.

audio_url() raises rather than guessing. A fetcher that downloads a not-ready object yields truncated files that look successful to the ledger — the worst available failure mode, since the recording is then marked seen and never retried.

processor/ — transcribe → route → execute Forge

Forge learns of new work by polling git, every 2 minutes:

flow
git pull --rebase  →  scan inbox/ for status:raw  →  work  →  commit  →  push

Rejected for v1: a GitHub webhook to a Forge endpoint (requires exposing inbound network on the box that runs an autonomous agent — a real attack surface), and repository_dispatch via Actions (same exposure, plus a moving part). Polling costs a git pull every two minutes and needs no firewall rule.

The split’s benefit is also its failure mode. Forge may be offline and work waits safely in git — but a dead Forge looks exactly like an idle one. Nothing errors; recordings just quietly pile up. T-74’s backlog alarm is what makes the queue safe to rely on.

Routing in v1 is deliberately dumb: the entire transcript becomes the prompt, with a preamble carrying the output contract. Keyword grammars and intent classification are v2 — build them when a real utterance demands it, not before.

Safety. The agent executes text derived from ambient audio. Anything within earshot of the pin can, in principle, become an instruction. For v1: unprivileged user, vault-scoped working directory, deny-by-default tool permissions, no credentials in scope beyond the vault deploy key. Every executed prompt is committed, so git history is the audit trail. This is a real surface, not a theoretical one.

ops/ — deployment

Two deploy targets from one repo:

install
./ops/install.sh wardog     # timer + ingest + Node/CLI checks
./ops/install.sh forge      # timer + processor + whisper/claude checks

No containers in v1 — both are single trusted hosts, and a container adds a layer without removing a problem.

Concurrent pushes

Both hosts commit to atticus-vault. Every push is git pull --rebase --autostash → push → bounded retry. They own disjoint paths — WarDog inbox/ + .state/, Forge processed/ + failures/ — so rebases apply cleanly. The one shared file is a recording’s metadata JSON when Forge advances status, and Forge only edits records already committed. Retry bounded at 3, then quarantine and notify rather than loop.

6. The Mac question

v1 needs no Mac. Everything through T-73 runs on Linux. Node, Python, faster-whisper, git, systemd — Forge handles all of it. The Mac only enters via W8, which is contingent and probably never triggers.

If W8 does trigger, a Mac is still avoidable, with friction:

NeedMac-free pathCost
Build + signGitHub Actions macos-latest runnerFree tier, or ~$0.08/min
Certs + profilesfastlane match + App Store Connect API keySetup complexity
Install to iPhoneTestFlight$99/yr Apple Developer
Iterate on BLE bugs—This is where it breaks down

Build-and-ship is genuinely Mac-free. Debugging is not. BLE work is empirical — you’ll be watching connection state, retry behavior, and background-suspension edge cases. Doing that through 10-minute CI round-trips with no debugger, no Xcode console, and no Instruments is miserable enough that it will dominate the schedule.

Recommendation: don’t buy a Mac now. If W8 triggers, borrow or rent one (MacStadium, ~$100/mo) for the BLE development window, then drop it and keep shipping via Actions.

7. Which Plaud product surface

Answer: none of them. The official CLI is paywalled — it requires a paid plan. We use a Plaud Web fetcher instead. See ADR-002.

SurfaceWhat it readsWhy not
CLI
@plaud-ai/cli		Your personal accountPaywalled.
MCP
@plaud-ai/mcp		Same account, same dataPaywalled the same way — and a cron job has no use for a conversational client.
EmbeddedNothing of yours: audio you upload, plus BLE pairingFree, but B2B infrastructure for building your own Plaud-powered app. No “list my recordings” endpoint. W8 only.

What we use instead

ingest/plaud_web.py
plaud_web.py login              # seed the session (interactive, once)
plaud_web.py whoami             # session health check
plaud_web.py list --json        # recordings, newest first
plaud_web.py audio <id> -o …    # download original MP3/WAV

Playwright with a persistent session, credentials from 1Password, calling Plaud’s JSON API with the session the browser established. Follows the house pattern in ~/.claude/site-fetchers/. Deliberately CLI-shaped, so nothing downstream of ingest changes. Cost: $0/yr.

Why the free tier is sufficient

Starter (free)Paid
Original audio export (MP3/WAV)✅✅
Wi-Fi sync to cloud✅✅

Two reasons the transcription allowance is irrelevant: we transcribe locally with faster-whisper, and AutoFlow only fires above 200 words — so a 15-second command consumes zero minutes. The free tier is not a compromise for this workload.

The tradeoff we accepted. The fetcher breaks if Plaud reworks their web app — the same bet the other five fetchers in the registry already make. It is why T-72’s session health check is load-bearing rather than nice-to-have, and why the T-06 discovery report is kept: re-running recon is how we repair a break.

Community packages

Avoid sergivalverde/plaud-toolkit and the rest. Reverse-engineered from the web app, alpha, and they want your email and password in plaintext.

Our fetcher targets the same underlying API, so the distinction matters: we authenticate through a real browser session in a 1Password-backed Playwright profile and never store the account password. Same access, none of the credential handling that made the toolkits a bad idea.

Free fallback worth remembering

The web API exposes Plaud’s transcript when one exists. Short commands won’t have one (AutoFlow’s 200-word floor), but meeting-length recordings arrive already transcribed at no cost. A “use Plaud’s if present, whisper otherwise” fallback is cheap. Not v1 — noted so it isn’t rediscovered.
