# Forge deployment report — 2026-07-29

Deploying the **processor half** on Forge (the AI server). Ingest runs
elsewhere. Code was not rebuilt; this is installation, verification, and an
honest account of what does not work.

**Host:** `forge`, Fedora 43 (`fc43`), kernel 7.0.14. Python 3.14.6, git 2.54.0,
requests 2.33.1, `claude` 2.1.220.

## Bottom line

The pipeline is deployed and the fixture ran end to end: speech → OpenAI
transcription → deep-research skill → one self-contained 47 KB HTML report →
three commits (`transcribe`, `route`, `publish`). The timer is enabled and
firing every 5 minutes.

Three real defects surfaced (installer `ReadWritePaths`; output-contract wiring;
and — worst — the systemd unit cannot find `claude`) plus one environment gap
(the agent had no web access). The fixture passed through all of them; only the
**real** systemd path on **real** recordings exposed #1 and #4. Since then the
ingest side went live, real recordings were processed end-to-end, and — at the
operator's request — a tailnet vault browser was added. Details below.

## What failed / defects

### 1. Installer never grants the systemd unit write access to the vault (CONFIRMED)

`ops/install.sh` intends to append the vault path to the service's
`ReadWritePaths=`. It does not, because its idempotency guard matches the
**commented example line** that already contains the vault path:

```sh
if ! grep -q "ReadWritePaths=.*$VAULT" "$UNITS/atticus-processor.service"; then
```

The unit template ships with `# ReadWritePaths=... /home/gregg/atticus-vault`
as a hint comment. `grep` finds it, the guard thinks the work is done, and the
`sed` that patches the *active* line never runs. The installer prints no
"granted the unit write access to the vault" line — that is the tell.

**Effect:** the active line stays `ReadWritePaths=/home/gregg/atticus %h/.claude
%h/.cache`, and with `ProtectHome=read-only` the vault is read-only inside the
sandbox. Proven with a matching transient unit:

```
touch: cannot touch '/home/gregg/atticus-vault/.write_probe': Read-only file system
```

The fixture did **not** catch this (it runs the pipeline directly, unsandboxed),
but under the timer the first real recording would fail at `git pull`/commit.

**Fix (one line, `ops/install.sh`):** anchor the guard to the active line only,
e.g. match `^ReadWritePaths=` and check the vault is not already on *that* line,
or strip comments before grepping. I did **not** change the code — see
"On-machine changes" for the local unit edit that makes this deployment work now.

### 2. Agent writes the deliverable to the vault path, but the pipeline watches a scratch dir (CONFIRMED)

`execute.build_task()` is handed the **vault** output dir as `{outdir}`, so the
task tells the agent *"Write every deliverable into
`.../.scratch-vault/processed/.../<stem>`"*. But `execute.run()` runs the agent
in a temp workspace and only collects files from that scratch `output/` dir
(`--add-dir`, `ATTICUS_OUTPUT_DIR`). The agent followed the written instruction
and wrote `agentic-harness.html` straight into the vault path; the scratch dir
stayed empty, so the pipeline logged:

```
[I]     agent wrote no files; saved its response as response.md
[I]     produced 1 file(s), 980 bytes
```

**Effects, all observed:**
- The real 47 KB report reached the vault only because the agent wrote there
  **directly** — not via the intended scratch → copy path.
- A spurious 980-byte `response.md` stub is committed next to the real report.
- Accounting is wrong: "1 file, 980 bytes" ignores the actual 47 KB HTML.
- **Safety regression.** The design (CLAUDE.md, SPEC §4.2, `execute.py`
  docstring) says the agent writes to scratch and never into the vault. Here it
  wrote into the vault tree — and because fix #1's local patch makes the vault
  writable under systemd, an agent could write anywhere under `~/atticus-vault`,
  a wider blast radius than intended.

**Suggested fix (maintainer's call — not applied):** give the agent a stable,
in-workspace target (e.g. `./output/`, or `$ATTICUS_OUTPUT_DIR`) in the
preamble instead of the absolute vault path, and keep the scratch → copy step
as the sole path into the vault.

### 3. The deep-research agent had no web access (ENVIRONMENT)

The flagship skill is supposed to "search the web, read primary sources."
In this run it could not — from the agent's own saved response:

> **WebSearch and WebFetch were both denied in this sandbox**, so nothing was
> fetched or verified. The report is written from model knowledge.

`execute.run()` invokes `claude -p --permission-mode acceptEdits` with no
`--allowedTools`; in a headless run with no TTY to approve them, `WebSearch`/
`WebFetch` default to denied. The agent handled it well (a prominent red
"unverified" callout, no fabricated figures), but the result is a
knowledge-only essay, not researched. If web research is intended for the
unattended pipeline, the processor must grant those tools explicitly
(`--allowedTools WebSearch WebFetch …`), which also interacts with the SPEC's
"deny-by-default tools" posture — a deliberate decision is needed.

### 4. The systemd unit cannot find `claude` (CONFIRMED on real data)

This is the one that actually broke real execution. systemd **user** services
run with `PATH=/usr/local/bin:/usr/bin` — which does **not** include
`~/.local/bin`, where the `claude` CLI lives on this box. So the first genuine
command recording (see the real-recording run below) passed the gate, routed,
and then died in the execute stage:

```
[E]   ✗ execution: claude binary not found: claude
```

The fixture and my direct runs never hit this, because an interactive shell has
`~/.local/bin` on `PATH` — only the sandboxed unit does not. `install.sh`'s
preflight even prints `✓ claude 2.1.220`, because it too runs in a normal shell.
So the check passes and the unit still can't launch the agent.

**Fix (belongs in `ops/atticus-processor.service`):** set the unit's PATH, e.g.

```ini
Environment=PATH=%h/.local/bin:/usr/local/bin:/usr/bin:/bin
```

Applied to the installed unit on-machine; after the fix the same recording
produced a 74 KB report. Left the repo template for the maintainer.

## Real-recording run — WarDog went live mid-deploy

During this deployment the ingest side (WarDog) started pushing **real**
recordings into the vault. With the operator's go-ahead they were processed.
This is the most useful result in the report, because it is the real pipeline on
real audio rather than a fixture:

- The **wake-phrase gate held**. Of the genuine recordings, all but one did not
  begin with "Atticus" and were correctly filed as unexecuted notes — the
  designed protection against a wearable acting on overheard speech.
- **A misheard wake word is a real failure mode, observed.** One recording
  transcribed as *"Advocates research the best Android phone options…"* —
  "Atticus" heard as "Advocates" — so a real command was gated as a note and
  never ran. Concrete instance of SPEC §4.2's concern, and part of the argument
  for the larger transcription model.
- **The one genuine command executed** (*"Atticus, research the top five
  platforms for an AI server…"*), after fix #4, and produced a **74 KB**
  self-contained HTML report — knowledge-only (defect #3), written straight into
  the vault with a stray `response.md` and `output_bytes` counting only the stub
  (defect #2). Both defects manifested exactly as described, on real output.
- **Agent run time for that report: ~11 minutes** (knowledge-only, no web).
  Inside the 30-minute budget; a web-enabled research pass would be longer and
  is still unmeasured.

## Vault browser (added at the operator's request)

A private, tailnet-only web view of the vault's HTML docs, with
**list / filter-by-tag / search**, now lives in the vault at `site/` and is
served through Forge's existing `forgeserve`:

```
http://forge/atticus/index.html      (tailnet peers only, never public)
```

`site/build.py` (stdlib only) scans `reports/` and `processed/`, renders
Markdown reports to styled HTML, and publishes a self-contained index; a user
timer (`site/install.sh` → `atticus-vault-site.timer`) rebuilds every 5 minutes.
Tags live in each recording's metadata JSON, auto-seeded from the date and
editable by hand. **Known limitation:** only HTML docs are indexed — gated
`note.md` files and transcripts do not yet appear (an easy addition, deferred).

## Machine differences from what the spec assumes

1. **`~/.config/ai/env` did not exist.** The spec/installer treat it as the
   machine's single credential source, but `OPENAI_API_KEY` was only present as
   an environment variable. Per instruction I stopped rather than working around
   it; with approval I created the file (600, dir 700) from the env var. If this
   box is expected to already have that file, something upstream did not run.
2. **Global gh credential helper makes HTTPS pushable.** `~/.gitconfig` sets
   `credential.https://github.com.helper = !gh auth git-credential`, and the
   active gh account is `beekeeper-lab` with `repo` scope — so a plain
   `git push` from `~/atticus` **would** succeed, contrary to "Forge must NOT be
   able to push to its own source." I neutralized it locally
   (`git config credential.https://github.com.helper ""` in `~/atticus`) and
   verified a dry-run push now fails auth. Pull still works (public repo).
3. **No TTS engine.** `espeak-ng` (needed by `mkfixture --say`) was absent and
   `sudo` is off-limits to the agent; you installed it. Worth adding to the
   Forge preflight/README so the fixture is runnable out of the box.
4. **Fedora, not a generic assumption.** Package installs on Forge use `dnf`.

## Elapsed time vs the 30-minute assumption

The pipeline run (transcription + agent) took **5 min 42 s** wall clock
(09:48:32 → 09:54:15 EDT). Comfortably inside the 1800 s (`ATTICUS_EXEC_TIMEOUT`)

**Important caveat:** this run made **no web calls** (defect #3), so it is not

path is unmeasured.
